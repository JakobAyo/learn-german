# Adopt a concern-based documentation structure

## Context

The project needed a single place to record how it works and why choices were made, in a form that both people and coding agents can navigate without reading everything.

## Decision

Documentation lives under `docs/`, split by concern following the single responsibility principle:

- `docs/decisions/` — Numbered decision records. Why the project is the way it is.
- `docs/product/` — Learning goals, scope, non-goals and roadmap of the extractor.
- `docs/learning-design/` — Card types, what each trains, Anki deck and note-type layout, review settings.
- `docs/system-design/` — Extraction pipeline: ingest, NLP processing, filtering and ranking, card generation, export.
- `docs/data/` — Input sources, frequency lists, known-words store and the extracted-item data model.
- `docs/integrations/` — External systems: Anki, LLM provider, dictionaries; how each is called and fails.
- `docs/development/` — Local setup, dependencies and NLP models, and how to run the extractor.
- `docs/research/` — Experiments, evaluations and summaries of outside advice that inform decisions.

Every folder carries a `CLAUDE.md` that states its scope and indexes its files. Every document carries frontmatter (`title`, `summary`, `status`, `updated`). Names are kebab-case. The index is generated by script and checked by a validator.

## Alternatives considered

- One flat folder of documents: rejected, it does not scale and agents must read everything to find anything.
- Grouping by document type (diagrams/, specs/, notes/): rejected, a reader looks for a concern, not a format.
- A wiki outside the repository: rejected, it drifts from the code and is invisible to agents.

## Consequences

- Adding a document means choosing one concern folder and writing frontmatter.
- Decisions must be recorded as they are made, or the log loses its value.
- A new concern that fits no folder gets a new folder and a decision record explaining it.
